# cbc_hb — Choice-Based Conjoint с оценкой полезностей методом Иерархического Байеса

Скрипт реализует полный цикл CBC-исследования: генерацию экспериментального
плана опроса и оценку индивидуальных полезностей (part-worth utilities)
иерархической байесовской моделью на PyMC.

## Установка

Нужен Python 3.10 или новее (код использует синтаксис `X | None` в аннотациях).

### Что именно ставится и зачем

| пакет | минимум | зачем нужен |
|---|---|---|
| `numpy` | 1.24 | матрицы плана, восстановление полезностей, все расчёты после сэмплирования |
| `pandas` | 2.0 | длинные таблицы плана и ответов, выгрузка результатов |
| `scipy` | 1.10 | подтягивается PyMC; напрямую модулем не используется |
| `pymc` | 5.10 | описание иерархической модели и сэмплер NUTS |
| `arviz` | 0.17 | диагностика сходимости: `r_hat`, ESS, дивергенции |
| `matplotlib` | 3.7 | график истории итераций |

Тяжёлый байесовский стек держится отдельно от корневого `requirements.txt`:
конвертеру `sav2adl` он не нужен, и ставить его тем, кто пользуется только
конвертером, незачем.

### Вариант 1: pip в виртуальном окружении

Самый простой путь. Виртуальное окружение желательно — PyMC тянет за собой
`pytensor`, который лучше не смешивать с системными пакетами.

```bash

source .venv/bin/activate        # Windows: .venv\Scripts\activate

```

### Если установка ломается

| симптом | причина и что делать |
|---|---|
| `ERROR: Cannot uninstall packaging ..., RECORD file not found` | pip пытается обновить пакет, поставленный системным менеджером (типично для Debian/Ubuntu). Ставьте в виртуальное окружение либо добавьте `--ignore-installed packaging` |
| `pip install` прошёл, но `import pymc` падает с `ModuleNotFoundError` | `pip` и `python` указывают на разные интерпретаторы. Ставьте через `python -m pip install ...` — так интерпретатор гарантированно тот же |
| `PyTensor could not link to a BLAS installation` | предупреждение, а не ошибка: считать будет, но медленнее. Снимается установкой через conda-forge |
| на Windows PyTensor падает при компиляции C-кода | нет компилятора. Поставьте `m2w64-toolchain` через conda либо отключите компиляцию: `set PYTENSOR_FLAGS=cxx=` (расчёт замедлится) |
| сэмплирование зависает без ошибки | многопроцессность не переживает окружение. Запускайте в одном процессе: `python cbc_hb.py single_choice 1` |

## Запуск демонстрации

```bash
python cbc_hb.py                # режим single_choice
python cbc_hb.py allocation     # режим распределения 100 баллов
python cbc_hb.py single_choice 1  # сэмплирование в одном процессе
```

Второй аргумент задаёт число процессов. Значение 1 отключает многопроцессный
сэмплинг: медленнее, но надёжнее в окружениях, где межпроцессное взаимодействие
рвётся — в контейнерах, которые засыпают, и на Windows без прогретого
`if __name__ == "__main__"`.

Демонстрация генерирует план на 30 респондентов с None-концептом и
взаимодействием Brand x Price, симулирует гетерогенных респондентов трёх
сегментов, оценивает HB-модель и печатает метрики, которые показывают,
насколько успешно восстановлены истинные скрытые параметры.

Считает она не быстро: 20 параметров при 30 респондентах требуют длинных цепей
(1500 итераций прогрева и 1500 финальных, 4 цепи), что занимает порядка 10-20
минут без оптимизированного BLAS. Более короткие цепи не дотягивают до
`r_hat < 1.01`, поэтому сокращать их — значит получать предупреждение о
несходимости вместо результата.

## Быстрый старт

```python
import pandas as pd
from cbc_hb import CBCDesignGenerator, CBCHierarchicalBayesEstimator

space = {
    "Brand":    ["Alpha", "Beta", "Gamma", "Delta"],
    "Price":    [299, 399, 499, 599],
    "Storage":  ["128GB", "256GB", "512GB"],
    "Warranty": ["1 year", "2 years", "3 years"],
}

generator = CBCDesignGenerator(
    space,
    attribute_cols=list(space),
    concepts_per_task=3,
    tasks_per_respondent=15,
    num_respondents=300,
    control_attributes="Brand",        # запрет повтора бренда внутри задачи
    interactions=[("Brand", "Price")], # план учитывает ячейки взаимодействия
    include_none=True,                 # добавить None-концепт в каждую задачу
    random_state=42,
)
design = generator.generate()

estimator = CBCHierarchicalBayesEstimator(
    attribute_cols=list(space),
    interactions=[("Brand", "Price")],
    response_mode="single_choice",     # либо "allocation"
    include_none=True,
    draws=1000,
    tune=500,
)
estimator.fit(design, responses)

estimator.individual_results_    # полезности + важность + RLH по респондентам
estimator.population_summary_    # сводка по выборке
estimator.plot_trace_history(path="trace.png")
```

## Форматы данных

### Вход: план опроса `design_df`

Длинная таблица — одна строка на одну альтернативу одной задачи одного
респондента.

| колонка | тип | обязательна | описание |
|---|---|---|---|
| `respondent_id` | любой хешируемый | да | идентификатор респондента |
| `task_id` | любой хешируемый | да | номер задачи выбора внутри респондента |
| `concept_id` | любой хешируемый | да | номер альтернативы внутри задачи |
| колонки атрибутов | любой хешируемый | да | по одной на атрибут, значение — уровень |
| `is_none` | 0/1 | только при `include_none=True` | признак строки None-концепта |

Пример плана на 3 атрибута с None-концептом:

```
respondent_id  task_id  concept_id  Brand  Price  Storage  is_none
            1        1           1  Alpha    299    256GB        0
            1        1           2  Gamma    499    256GB        0
            1        1           3   <NA>   <NA>     <NA>        1
            1        2           1   Beta    299    128GB        0
```

Требования, которые проверяются до запуска MCMC:

* тройка `(respondent_id, task_id, concept_id)` уникальна;
* число альтернатив одинаково во всех задачах;
* число задач одинаково у всех респондентов;
* у каждого атрибута не меньше двух уровней;
* при `include_none=True` — ровно один концепт с `is_none == 1` в каждой задаче,
  и атрибуты в этой строке пустые (`NaN`/`None`, а не служебный уровень вроде
  строки `"none"`: иначе он будет распознан как обычный уровень атрибута).

Уровни атрибутов **не задаются вручную** — они считываются из данных. Порядок
детерминирован: числовые уровни сортируются по значению, остальные
лексикографически, и последний становится референсным. Референсный уровень
влияет только на внутреннее кодирование: в выдаче присутствуют полезности всех
уровней.

### Вход: ответы `responses_df`

Схема одна на оба режима — идентификаторы плюс одна числовая колонка ответа.
Имя колонки берётся первым из `response`, `chosen`, `allocation`; это синонимы,
а не разные форматы.

| колонка | тип | описание |
|---|---|---|
| `respondent_id`, `task_id`, `concept_id` | как в плане | должны совпадать с планом один в один |
| `response` (или `chosen` / `allocation`) | число | значение зависит от режима |

**Режим `single_choice`** — значения 0/1, ровно одна единица на задачу:

```
respondent_id  task_id  concept_id  response
            1        1           1         1
            1        1           2         0
            1        1           3         0
```

**Режим `allocation`** — неотрицательные числа с одинаковой суммой во всех
задачах. Нули допустимы, дробные значения тоже:

```
respondent_id  task_id  concept_id  response
            1        1           1      92.9
            1        1           2       0.0
            1        1           3       7.1
```

Сумма задаётся параметром `allocation_total`. Если он не указан, берётся сумма
первой задачи и того же требуют от остальных — то есть опечатка в одной строке
не пройдёт незамеченной.

Ответ должен быть для каждой строки плана: если хоть одна строка осталась без
ответа, расчёт останавливается с указанием их количества.

### Чтение из файлов

Модуль работает с `DataFrame`, а не с файлами напрямую, поэтому подойдёт любой
источник, который читает pandas:

```python
import pandas as pd

design = pd.read_csv("design.csv")
responses = pd.read_csv("responses.csv")

# или из Excel
design = pd.read_excel("study.xlsx", sheet_name="design")
responses = pd.read_excel("study.xlsx", sheet_name="responses")
```

Про типы стоит знать две вещи.

Числовые уровни переживают запись в CSV и чтение обратно, даже если превращаются
из `299` в `299.0`: Python считает эти значения равными, и распознавание уровней
не ломается. Изменятся только имена колонок в выдаче — `Price=299.0` вместо
`Price=299`.

А вот смешение чисел со строками ломает всё: если уровни объявлены как `[299,
499]`, а в данных лежат `"299"` и `"499"` (или наоборот), расчёт остановится с
сообщением `атрибут 'Price': неизвестные уровни ['299', '499']`. Это бывает при
чтении с `dtype=str`. Держите атрибуты в одном типе во всех источниках.

### Выход: `individual_results_`

Главная таблица результатов. Индекс — `respondent_id`, по строке на человека.
Колонки идут группами:

| группа | пример имени | что означает |
|---|---|---|
| полезности уровней | `Brand=Alpha`, `Price=299` | по одной колонке на каждый уровень каждого атрибута, включая референсный |
| ячейки взаимодействий | `Brand=Alpha x Price=299` | полная таблица `K_a × K_b` для каждой объявленной пары |
| константа None | `None` | только при `include_none=True` |
| важность атрибутов | `Brand_Importance` | проценты, сумма по строке ровно 100 |
| качество посадки | `RLH`, `RLH_null` | посадка респондента и ориентир случайного выбора |

Сохраняется как обычный `DataFrame`:

```python
estimator.individual_results_.to_csv("utilities.csv", encoding="utf-8")
estimator.individual_results_.to_excel("utilities.xlsx")
```

Полезности внутри атрибута в сумме дают ноль, а при `normalization="zcd"`
дополнительно отмасштабированы так, что средний размах атрибута равен 100 —
это делает людей сопоставимыми между собой.

### Выход: `population_summary_`

Сводка по выборке в длинном формате: по строке на каждую величину.

| колонка | описание |
|---|---|
| `kind` | `utility`, `interaction`, `none`, `importance` или `fit` |
| `attribute` | атрибут, пара атрибутов или имя показателя |
| `level` | уровень (пусто для важности и `fit`) |
| `mean`, `std` | среднее и стандартное отклонение по респондентам |

```
   kind attribute level    mean    std
utility     Brand Alpha  72.092  3.623
utility     Brand  Beta -32.365 14.682
```

Важность здесь — среднее индивидуальных процентов, а не важность, посчитанная
из средних полезностей: это разные числа, и Sawtooth считает первым способом.

### Выход: остальные атрибуты и методы

| что | тип | содержимое |
|---|---|---|
| `interaction_tables_` | `dict` пара → `DataFrame` | таблицы взаимодействий отдельно от общей выдачи |
| `utilities_raw_` | `DataFrame` | полезности без ZCD-нормализации, для сверки с внешними расчётами |
| `diagnostics_` | `dict` | `max_r_hat`, `min_ess_bulk`, `divergences`, `n_params`, `upper_level_cov`, `summary` |
| `sparsity_report_` | `DataFrame` | заполненность ячеек взаимодействий по респондентам |
| `beta_mean_` | `ndarray (N, P)` | апостериорные средние в закодированном пространстве |
| `idata_` | `arviz.InferenceData` | полная апостериорная выборка вместе с прогревом |
| `predict_utilities(design)` | `ndarray` | суммарная полезность каждой строки плана |
| `hit_rate(design, responses)` | `float` | доля задач с угаданной лучшей альтернативой |
| `share_metrics(design, responses)` | `dict` | `mae`, `rmse`, `correlation` по долям выбора |
| `plot_trace_history(...)` | `Figure` | график истории итераций |

## Сценарий: режим single_choice

Полный цикл от плана до выгрузки полезностей.

```python
import pandas as pd
from cbc_hb import CBCDesignGenerator, CBCHierarchicalBayesEstimator

space = {
    "Brand":    ["Alpha", "Beta", "Gamma", "Delta"],
    "Price":    [299, 399, 499, 599],
    "Storage":  ["128GB", "256GB", "512GB"],
    "Warranty": ["1 year", "2 years", "3 years"],
}

# 1. План опроса
generator = CBCDesignGenerator(
    space,
    attribute_cols=list(space),
    concepts_per_task=3,          # реальных профилей на экране
    tasks_per_respondent=15,
    num_respondents=300,
    control_attributes="Brand",   # бренд не повторяется внутри задачи
    interactions=[("Brand", "Price")],
    include_none=True,            # плюс вариант «ничего не выберу»
    random_state=42,
)
design = generator.generate()

# Проверить план до полевых работ
print(generator.check_prohibitions())        # ожидается пустой словарь
print(generator.balance_report())
print(generator.interaction_report())        # пустые ячейки видны здесь
print(f"D-эффективность: {generator.d_efficiency_:.3f}")

design.to_csv("design.csv", index=False)     # отдать в систему опроса

# 2. Ответы возвращаются из поля в том же длинном формате
responses = pd.read_csv("responses.csv")     # колонка response: 0/1

# 3. Оценка
estimator = CBCHierarchicalBayesEstimator(
    attribute_cols=list(space),
    interactions=[("Brand", "Price")],
    response_mode="single_choice",
    include_none=True,
    draws=1500,
    tune=1500,
    chains=4,
)
estimator.fit(design, responses)

# 4. Диагностика — до того, как смотреть на числа
print(estimator.diagnostics_["max_r_hat"])      # нужно <= 1.01
print(estimator.diagnostics_["divergences"])    # нужно 0

# 5. Результаты
estimator.individual_results_.to_csv("utilities.csv", encoding="utf-8")
estimator.population_summary_.to_csv("summary.csv", index=False, encoding="utf-8")
estimator.plot_trace_history(path="trace.png")
```

Валидация на отложенных задачах, если часть задач не участвовала в оценке:

```python
fit_mask = design["task_id"] <= 12
estimator.fit(design[fit_mask], responses[responses["task_id"] <= 12])

holdout = design[~fit_mask]
holdout_responses = responses[responses["task_id"] > 12]
print(estimator.hit_rate(holdout, holdout_responses))
```

## Сценарий: режим allocation

Отличий от предыдущего сценария ровно два: чем заполнена колонка ответа и как
измеряется качество.

```python
# План строится точно так же
design = generator.generate()

# Ответы: сумма баллов в каждой задаче одинакова
responses = pd.read_csv("allocations.csv")   # колонка response: например 20/55/25

estimator = CBCHierarchicalBayesEstimator(
    attribute_cols=list(space),
    interactions=[("Brand", "Price")],
    response_mode="allocation",
    include_none=True,
    allocation_total=100,      # ожидаемая сумма; None — определить по первой задаче
    allocation_weight=1.0,     # вес задачи в единицах одного выбора
    draws=1500,
    tune=1500,
)
estimator.fit(design, responses)

# Для аллокаций содержательна точность долей, а не попадание в максимум
print(estimator.share_metrics(holdout, holdout_responses))
# {'mae': 0.099, 'rmse': 0.14, 'correlation': 0.887}
```

Про `allocation_weight` стоит прочитать раздел «Режим allocation: вес
наблюдения» ниже: значение по умолчанию выбрано консервативно, и увеличивать его
имеет смысл осознанно.

Выдача устроена одинаково в обоих режимах — те же полезности, та же важность, те
же таблицы взаимодействий. Различается только `RLH`: в `single_choice` это
классическая метрика Sawtooth, в `allocation` — та же величина, взвешенная по
долям баллов.

## Модуль 1: `CBCDesignGenerator`

Строит рандомизированный сбалансированный план и возвращает длинный DataFrame с
колонками `respondent_id`, `task_id`, `concept_id` и метками уровней. Матрица
эффект-кодирования доступна через `design_matrix()` — метки при этом остаются
рядом, они нужны для отчётности и отладки.

**Запрет дублирования (between-concept prohibitions).** Уровни атрибутов из
`control_attributes` не повторяются внутри одной задачи. Это защищает от
доминирующих альтернатив вида «тот же бренд дважды, но дешевле». Ограничение
соблюдается по построению: внутри задачи уровни выбираются без возврата, среди
допустимых предпочитается наименее использованный. Если у контрольного атрибута
уровней меньше, чем концептов в задаче, конструктор сразу падает с объяснением —
такое ограничение невыполнимо.

**Баланс и D-эффективность.** Частоты уровней выравниваются по построению
(перемешанные колоды вместо независимого сэмплирования), после чего из
`n_starts` случайных стартов выбирается план с лучшей D-эффективностью. Метрика
считается относительно теоретического ортогонального идеала, поэтому она
абсолютна: 1.0 — идеальный план, 0.0 — вырожденный. Оптимизируется **средняя
эффективность индивидуальных блоков**, поскольку в HB полезности оцениваются для
каждого респондента отдельно.

Отчёты: `balance_report()`, `interaction_report()`, `check_prohibitions()`.

## Модуль 2: `CBCHierarchicalBayesEstimator`

### Единая схема ответов

`responses_df` имеет одну схему на оба режима: идентификаторы плюс одна
числовая колонка ответа. Её имя берётся первым из `response`, `chosen`,
`allocation` — это синонимы, а не разные форматы. Режим меняет правила
проверки, но не структуру данных.

| response_mode | правило | пример значений в задаче |
|---|---|---|
| `single_choice` | значения 0/1, ровно одна единица | `0, 1, 0` |
| `allocation` | неотрицательные числа с фиксированной суммой | `20, 55, 25` |

```
respondent_id | task_id | concept_id | response
            1 |       1 |          1 |       20
            1 |       1 |          2 |       55
            1 |       1 |          3 |       25
```

Сумма для `allocation` задаётся параметром `allocation_total`; если он не задан,
берётся сумма первой задачи, и того же требуют от остальных. Модель требует
одинакового числа задач у респондентов и одинакового числа альтернатив в
задачах — это проверяется до запуска MCMC.

### None-концепт

`include_none=True` добавляет альтернативу «не выбрал бы ничего». Генератор
создаёт её сам: `concept_id = concepts_per_task + 1`, признак `is_none = 1`,
пропуски во всех атрибутах. Обратите внимание, что `concepts_per_task` задаёт
число *реальных* профилей, а None добавляется сверх него.

Оценивается None как индивидуальная константа альтернативы (ASC) — параметр
`None` в выдаче. Он не принадлежит ни одному атрибуту, поэтому не участвует ни в
ограничении нулевой суммы, ни в расчёте важности; в баланс уровней, запреты и
D-эффективность строки None тоже не входят.

Флаги ортогональны: `include_none` и `response_mode` комбинируются свободно,
включая распределение баллов с учётом варианта «ничего».

### Режим allocation: вес наблюдения

Распределение баллов моделируется взвешенным логарифмическим правдоподобием, а
не `pm.Multinomial` с `n = allocation_total`. Разница принципиальна:
мультиномиальное правдоподобие трактует 100 распределённых баллов как 100
независимых выборов, тогда как это одно суждение, выраженное на шкале.

На замере (8 респондентов, 10 задач) переход от веса 1 к весу 100 сужает
апостериорные интервалы индивидуальных полезностей примерно втрое; коэффициент
зависит от того, насколько сильно шринкедж верхнего уровня удерживает
индивидуальные оценки, и растёт с числом задач. Опасность в том, что
диагностика при этом молчит: `r_hat`, ESS и число дивергенций выглядят
нормально, а интервалы уже занижены.

`allocation_weight` задаёт информативность одной задачи в единицах «одного
выбора». Значение 1.0 (по умолчанию) консервативно; 2–3 защитимы, если считать,
что аллокация несёт больше информации, чем принудительный выбор. Установка веса
равным сумме баллов воспроизводит наивное поведение и не рекомендуется.

Для аллокаций основная метрика качества — `share_metrics()`: MAE, RMSE и
корреляция между предсказанными и фактическими долями внутри задачи.
`hit_rate()` тоже работает (сравнивает альтернативу с максимальной долей), но
игнорирует всё распределение баллов, кроме максимума.

### Структура модели

Нижний уровень — мультиномиальный логит: вероятность выбора есть softmax от
`X · beta_i`. Верхний уровень — `beta_i ~ N(alpha, D)`, записанный в
**нецентрированном** виде `beta_i = alpha + L · z_i`, где `z_i ~ N(0, I)`, а `L` —
фактор Холецкого из приора LKJ.

Нецентрированная параметризация здесь не стилистический выбор. Прямая запись
иерархии создаёт воронкообразную геометрию апостериорного распределения, на
которой NUTS систематически расходится, и никакой приор на ковариацию этого не
лечит — проблема в геометрии, а не в приоре.

### Эффекты взаимодействия

Параметр `interactions=[("Brand", "Price")]` добавляет взаимодействия первого
порядка: `(K_a − 1) × (K_b − 1)` колонок, равных произведениям колонок главных
эффектов. Полная таблица восстанавливается как `E_a · Γ · E_bᵀ` и имеет нулевые
суммы по строкам и по столбцам — ограничение Sawtooth соблюдается по построению.
Таблицы доступны в `interaction_tables_` и продублированы колонками в
`individual_results_`.

**Разреженность.** Взаимодействие 4×4 при 15 задачах по 3 концепта даёт около
2.8 наблюдения на ячейку у респондента, и часть ячеек может не показаться вовсе.
Перед запуском MCMC печатается отчёт о заполненности; при пустых ячейках
выдаётся предупреждение, что соответствующие индивидуальные параметры не
идентифицированы данными и держатся на шринкедже от верхнего уровня.

**Ковариация верхнего уровня.** Главная опасность взаимодействий — не сама
разреженность, а взрывной рост матрицы `D`. Для 19 параметров полная ковариация
содержит 190 свободных значений; при выборке в 30 респондентов это гарантированное
переобучение. Управляется параметром `upper_level_cov`:

| режим | структура | параметров `D` при P=19 |
|---|---|---|
| `full_lkj` | полная LKJ по всем параметрам | 190 |
| `block_lkj` | LKJ по структурному блоку + диагональ по взаимодействиям | 64 |
| `diagonal` | независимые дисперсии | 19 |
| `auto` | `full_lkj` без взаимодействий, `block_lkj` с ними | — |

Структурный блок — это главные эффекты плюс константа None-концепта; порядок
колонок кодирования (главные эффекты, None, взаимодействия) выбран именно так,
чтобы этот блок был непрерывным.

Дополнительно интеракционные члены регуляризуются: их средние получают более
узкий приор (`prior_alpha_sd_interaction`), масштабы — `HalfNormal` с малой
сигмой (`interaction_sd_prior`). При взаимодействиях `target_accept` по умолчанию
поднимается до 0.95.

> **Методологическая оговорка.** HB с индивидуальной гетерогенностью часто сам
> поглощает то, что в агрегированном логите выглядит как взаимодействие: разброс
> индивидуальных полезностей объясняет те же данные. Sawtooth рекомендует сначала
> проверять значимость взаимодействия на агрегированной модели и добавлять его в
> HB только при явном выигрыше на отложенных задачах. Сравнивайте варианты по
> `hit_rate()` на holdout, а не по подгонке к обучающим данным.

### Нормализация и важность атрибутов

Полезность референсного уровня восстанавливается как минус сумма оценённых
уровней атрибута, поэтому сумма полезностей внутри атрибута строго равна нулю.
Отдельного «центрирования» не требуется — при эффект-кодировании оно
выполняется по построению.

`normalization="zcd"` (по умолчанию) применяет zero-centered diffs: полезности
респондента домножаются на `100 · n_attributes / сумма размахов`, приводя средний
размах атрибута к 100. Без этого полезности несопоставимы между людьми: у
«шумного» респондента все коэффициенты меньше просто из-за масштаба логита.
`normalization="raw"` отключает масштабирование.

Важность атрибута — размах его полезностей, делённый на сумму размахов, в
процентах. Считается **на каждой итерации MCMC и усредняется**: размах нелинеен,
поэтому `importance(mean(beta)) ≠ mean(importance(beta))`. По той же причине
популяционная важность в `population_summary_` — это среднее индивидуальных
процентов, а не важность, посчитанная из средних полезностей.

`importance_mode`:

* `"main"` (по умолчанию) — важность по главным эффектам, как в Sawtooth:
  интеракционный член не принадлежит ни одному атрибуту по отдельности.
* `"joint"` — взаимодействующая пара отчитывается одной строкой
  `Brand*Price_Importance` по размаху совместной таблицы полезностей. Требует,
  чтобы атрибут участвовал не более чем в одном взаимодействии.

В обоих режимах сумма важностей по респонденту строго равна 100%.

### Диагностика

После сэмплирования собираются `max_r_hat`, `min_ess_bulk` и число расходящихся
переходов; предупреждения выдаются при `r_hat > 1.01`, ненулевых дивергенциях и
`ESS < 400`. Метрика посадки по респондентам — `RLH`, взвешенное по ответу
среднее геометрическое вероятностей. Для `single_choice` веса — индикатор
выбранной альтернативы, и формула совпадает с определением Sawtooth; для
`allocation` веса — доли распределённых баллов, то есть то же самое, обобщённое
на непрерывный ответ. Ориентир случайного выбора — единица, делённая на число
альтернатив в задаче (с учётом None-концепта), он же в колонке `RLH_null`.

### График истории итераций (Trace Plot)

```python
estimator.plot_trace_history(var_names=("alpha",), max_params=10, path="trace.png")
```

Серая зона — итерации прогрева (burn-in), белая — финальные draws, граница
отмечена пунктиром. Прогрев доступен потому, что `fit()` вызывает `pm.sample` с
`discard_tuned_samples=False`: по умолчанию PyMC выбрасывает tune-итерации, и в
серой зоне было бы нечего рисовать.

## Отличия от Sawtooth Software CBC/HB

Совпадает: эффект-кодирование, нулевая сумма полезностей внутри атрибута,
структура взаимодействий, zero-centered diffs, расчёт важности через размахи,
метрика RLH.

Отличается сознательно: Sawtooth использует MH-within-Gibbs с приором
inverse-Wishart на ковариацию верхнего уровня, здесь применяется NUTS с приором
LKJ на фактор Холецкого. LKJ гарантирует положительную определённость и
разделяет дисперсии и корреляции, что заметно устойчивее численно. Следствие:
числа не обязаны совпадать с выгрузкой Sawtooth побитово, хотя содержательно
эквивалентны.

## Ограничения

* Поддерживаются `single_choice` и `allocation`. Dual-response None (сначала
  выбор среди реальных концептов, затем отдельный вопрос о готовности купить)
  не реализован — доступен только классический None как альтернатива на экране.
* План должен быть сбалансирован: одинаковое число задач у респондентов и
  альтернатив в задачах.
* Цена трактуется как категориальный атрибут (поведение Sawtooth по умолчанию),
  линейная спецификация не предусмотрена.
* NUTS по индивидуальным параметрам масштабируется хуже, чем Gibbs: на выборках
  в несколько сотен респондентов расчёт занимает десятки минут. Для больших
  выборок имеет смысл подключить `nutpie` или `numpyro` в качестве бэкенда.

## Заметки по окружению

Как чинить конкретные сбои установки — в таблице в разделе «Если установка
ломается». Здесь то, что относится уже к расчётам.

PyMC компилирует модель через PyTensor при первом запуске, поэтому между
стартом скрипта и началом сэмплирования проходит несколько секунд — это
компиляция, а не зависание. Результат кешируется, повторные запуски с той же
структурой модели стартуют быстрее.

Скорость расчёта определяется в первую очередь наличием оптимизированного BLAS,
а не числом ядер: без него разница достигает нескольких раз. Многопроцессность
даёт выигрыш только до числа цепей — ставить `cores` больше `chains`
бессмысленно.

Первый запуск демонстрации удобно делать с укороченными цепями, чтобы убедиться,
что всё работает, и не ждать полный расчёт:

```python
import cbc_hb
cbc_hb.main(draws=300, tune=300)   # быстрая проверка, r_hat не сойдётся
```

## Тесты

```bash
python tests/test_cbc_hb.py
```

Проверяется детерминированная часть — кодирование, восстановление полезностей и
таблиц взаимодействия, соблюдение запретов, баланс, отчёт о разреженности и
валидация входных данных обоих режимов ответа. MCMC не запускается, поэтому
тест отрабатывает за секунды.

Отдельно сверяются две ветви правдоподобия: на one-hot ответах с весом 1 режим
`allocation` обязан дать ровно то же значение, что и `pm.Categorical`, — и даёт
его побитово. Это единственная проверка, которой нужен установленный PyMC; без
него она пропускается, остальные работают.

# pySmartSPSSExporter — GUI-конвертер SPSS (.sav) в fixed ASCII и Excel

Оконное приложение на tkinter: читает файл SPSS, определяет структуру переменных
и выгружает данные в трёх форматах — фиксированный ASCII с файлом разметки,
Excel с текстовыми ответами и Excel со всеми данными, где коды заменены на метки
значений.

## Установка и запуск

```bash
pip install -r requirements.txt
python pySmartSPSSExporter.py
```

`tkinter` входит в стандартную библиотеку, но в некоторых сборках Linux ставится
отдельно: `sudo apt install python3-tk`. Без `openpyxl` приложение запустится, но
кнопки выгрузки в Excel останутся заблокированными — это проверяется при старте.

## Как устроена работа

Порядок действий задан нумерацией кнопок в окне.

1. **Выбрать исходный `.sav`.** Чтение идёт в фоновом потоке с индикатором
   прогресса, окно не подвисает. Первая колонка файла безусловно
   переименовывается в `Rid` и считается идентификатором респондента.
2. **Настроить переменные ASCII.** Открывается таблица со структурой: имя,
   начальная и конечная позиция, длина, диапазон. Здесь выделяются переменные,
   которые нужно исключить из выгрузки. `Rid` исключить нельзя.
3. **Настроить строки для Excel.** То же самое для текстовых переменных, с
   показом числа заполненных ответов по каждой.
4. **Запустить экспорт.** Рядом с исходным файлом появляются `<имя>_exp.dat` и
   `<имя>_exp.lay`.

### Как переменные делятся на числовые и текстовые

Решение принимается по фактическому содержимому, а не только по типу SPSS:

* числовая по типу SPSS — идёт в ASCII;
* строковая, но полностью пустая — отбрасывается;
* строковая, но все непустые значения выглядят как числа (`^-?[0-9]+([.,][0-9]+)?$`) —
  запятая заменяется на точку, колонка приводится к числу и идёт в ASCII;
* остальные строковые — идут в выгрузку Excel.

### Выравнивание ширины по префиксу

Ширина колонки в `.dat` определяется самым длинным значением. После этого
колонки с общим префиксом до первого подчёркивания (`Q1_1`, `Q1_2`, `Q1_3`)
получают общую ширину, равную максимуму по группе. Это нужно, чтобы блоки
однотипных вопросов читались единообразно.

### Опциональное переименование в `.lay`

Флажок «Преобразовывать имена переменных через `xr`» включает два правила:

| исходное имя | результат | условие |
|---|---|---|
| `Q1_2.3` | `Q1xr3_2` | ровно одно подчёркивание, ровно одна точка |
| `Q1.3` | `Q1xr3` | без подчёркиваний, ровно одна точка |

Имена, не подходящие ни под одно правило, остаются без изменений. Переименование
затрагивает только `.lay` — данные в `.dat` не меняются.

## Форматы выгрузки

| файл | содержимое |
|---|---|
| `<имя>_exp.dat` | фиксированный ASCII: значения выровнены вправо в колонках заданной ширины, кодировка cp1251 |
| `<имя>_exp.lay` | разметка через табуляцию без заголовка: `Variable`, `Start`, `End`, `Length`, `Range` |
| `<имя>_open.xlsx` | `Rid` и выбранные текстовые переменные |
| файл с метками | все колонки исходного файла, коды заменены на метки значений из метаданных SPSS |

Пустые числовые значения выгружаются как пробелы соответствующей ширины.

## Разбор реализации

Ниже — результат разбора кода. Часть замечаний подтверждена замерами, они
приведены. Ничего из этого пока не исправлено: файл перенесён в папку как есть.

### 1. Артефакты float раздувают ширину колонок — самое серьёзное

Функция `format_val` форматирует дробные значения через `f"{val}"`, то есть
через стандартное представление float:

```python
if val == int(val): return str(int(val))
return f"{val}".rstrip("0").rstrip(".")
```

Значение `0.1 + 0.2` даёт строку `'0.30000000000000004'` длиной 19 символов.
Дальше эта длина становится шириной колонки, а выравнивание по префиксу
распространяет её на всю группу:

```
ширина до выравнивания:    {'Q1_1': 1, 'Q1_2': 19, 'Q1_3': 1, 'Q2_1': 1}
после выравнивания:        {'Q1_1': 19, 'Q1_2': 19, 'Q1_3': 19, 'Q2_1': 1}
длина строки .dat:         58 символов вместо 4
```

Одно значение раздувает файл в 14 раз. На реальных данных с дробями это не
теоретический риск, а обычное поведение арифметики с плавающей точкой.

Отдельно: научная нотация не обрабатывается — `1e-05` превращается в `1e-5`
из-за `rstrip("0")`, что для фиксированного ASCII бессмысленно.

Лечится форматированием с явной точностью, например `f"{val:.{n}f}"` с
округлением до разумного числа знаков, либо `decimal` с квантованием.

### 2. Сборка ASCII-строки в 5–8 раз медленнее необходимого

```python
ascii_data = pd.concat(formatted_cols, axis=1).apply("".join, axis=1)
```

`apply(..., axis=1)` идёт построчно на уровне Python. Замер на матрице
20000 × 300:

| способ | время |
|---|---|
| `apply` построчно (текущий код) | 14.98 с |
| `functools.reduce(operator.add, ...)` по Series | 2.78 с |
| суммирование object-массивов numpy | 1.97 с |

Результаты всех трёх способов совпадают побитово. Замена — одна строка.

### 3. Жёсткая кодировка cp1251 без обработки ошибок

```python
with open(dat_path, "w", encoding="cp1251") as f_dat:
```

Любой символ вне cp1251 роняет экспорт с `UnicodeEncodeError` уже после всей
обработки. Соседний `sav2adl.py` эту же ситуацию обрабатывает через
`errors="replace"` и умеет переключаться на UTF-8 ключом. Здесь ни того, ни
другого нет.

### 4. Одна выгрузка Excel блокирует интерфейс

`export_all_with_labels_to_excel` уходит в фоновый поток, а
`export_strings_to_excel` вызывает `to_excel` прямо в обработчике кнопки. На
большом файле окно замирает без индикации. Непоследовательно: механизм фоновой
работы в коде уже есть, просто не применён.

### 5. Расчёт позиций скопирован трижды

Один и тот же блок вычисления `start`/`end`/`range` повторяется в
`show_variable_selection_window`, во вложенной `reset_exceptions` и в
`_export_worker`. Три копии обязаны давать одинаковый результат, но ничем не
связаны — правка в одном месте молча разойдётся с остальными. Просится в
отдельный метод.

### 6. Повторное чтение файла с диска

`_export_labels_worker` заново читает весь `.sav`, хотя данные уже загружены в
`self.df` и `self.string_df`. Это оправдано тем, что нужны все колонки, включая
отброшенные при загрузке, — но тогда логичнее один раз сохранить полный кадр,
чем читать файл дважды.

### 7. Мелочи

* `import re` внутри `_export_worker`, хотя модуль импортирован на 7-й строке;
* `_update_progress` планирует два отдельных вызова `root.after` там, где хватит одного;
* `self.string_counts` не очищается при загрузке нового файла — накапливает ключи от предыдущего;
* диапазон в `.lay` формируется как `0-999...`, что неверно для отрицательных значений: знак минуса занимает позицию, но в диапазоне не отражён;
* `hasattr(self, 'btn_export_labels')` в `_unlock_main_buttons` намекает на неопределённость порядка создания виджетов.

### Что сделано хорошо

Стоит отметить и сильные стороны, чтобы разбор не выглядел односторонним.

Работа с потоками сделана корректно: тяжёлые операции вынесены в
`threading.Thread`, а возврат в GUI-поток идёт строго через `root.after` — это
именно то, чего требует tkinter, и распространённая ошибка обращения к виджетам
из фонового потока здесь не допущена. Прогресс обновляется дозированно (раз в 5
колонок), чтобы не заваливать очередь событий. Отсутствие `openpyxl` проверяется
при старте и приводит к блокировке кнопок, а не к падению при нажатии.

## Известные допущения

* Первая колонка файла всегда считается идентификатором и переименовывается в
  `Rid` без подтверждения. Если это не так, данные будут подписаны неверно.
* Кодировка выгрузки фиксирована как cp1251, ключа для UTF-8 нет.
* Группировка по префиксу берёт часть имени до первого подчёркивания и не
  настраивается.
